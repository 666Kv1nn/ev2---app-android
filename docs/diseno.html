Monitor IoT: diseño de la solución

TI3042 Aplicaciones Móviles para IoT · Unidad 2 · Paso 2

Aplicación Android para ver los sensores y controlar los actuadores conectados a una Raspberry Pi desde dos o más celulares. Los usuarios, las lecturas y la bitácora se guardan en MySQL en AWS RDS.

La app no se conecta directo a la base de datos. Le pide todo a la API de la Raspberry Pi, que es la única que tiene la contraseña de RDS. Así la contraseña no queda dentro del APK.

2. Comunicación inalámbrica

Elección: Wi-Fi con peticiones HTTPS a una API REST en la Raspberry Pi.

OpciónDistanciaConsumo de energíaEstabilidad
Wi-Fi + HTTPS30 a 50 m dentro de un edificioMedio. El celular solo consulta con la app abierta y la Pi está enchufadaBuena. Varios celulares a la vez, con reintento si se corta
BluetoothUnos 10 mBajoHay que emparejar y se corta al alejarse. Difícil con 2 celulares
MQTTIgual que Wi-FiBajoBuena, pero hay que instalar y asegurar un broker aparte

Wi-Fi permite que varios celulares usen el mismo servidor, y la Pi ya tiene internet para llegar a AWS. La app consulta cada 3 segundos y la Pi cada 1 segundo, que alcanza para el monitoreo.

3. Login y autenticación

Elección: API con MySQL. El login se valida en una API PHP contra la base de MySQL en AWS RDS (database-1.cujwinzrlr3q.us-east-1.rds.amazonaws.com).

OpciónSeguridadEscalabilidadFacilidad
SQLite (local)Cada celular tendría sus propios usuarios y no se pueden quitar accesosNo sirve para varios celularesMuy fácil
FirebaseAltaAltaFácil, pero los datos quedarían separados de MySQL
API + MySQL (AWS RDS)Alta: contraseñas con hash, tokens y roles revisados en el servidorAlta: RDS se puede agrandar y la API se puede copiar a otro servidorMedia: usa PHP y MySQL, como en la unidad anterior, y todo queda en una sola base

Cómo funciona

  1. La app manda usuario y contraseña por POST a login.php, por HTTPS.
  2. Si la cuenta tiene 5 intentos fallidos en 15 minutos, se bloquea por 15 minutos.
  3. La API compara la contraseña con el hash bcrypt guardado en la tabla usuarios.
  4. Si es correcta, crea un token aleatorio. En la tabla sesiones se guarda solo su hash, con 12 horas de duración.
  5. La app guarda el token cifrado con EncryptedSharedPreferences y lo manda en cada petición (Authorization: Bearer).
  6. Si el token vence o el admin desactiva la cuenta, la API responde 401 y la app vuelve al login.

Roles: el administrador hace todo y crea usuarios; el operador ve y controla los dispositivos; el lector solo ve. No hay registro abierto: las cuentas las crea el administrador.

6. Interacción con los dispositivos IoT

  • Lecturas: el agente de la Raspberry Pi lee los sensores cada 10 s y los manda a la API, que los guarda en la tabla lecturas.
  • Visualización: el panel muestra el último valor de cada sensor y el detalle muestra el gráfico con el rango permitido. Si un valor sale del rango se pinta de rojo, aparece un aviso y se registra en la bitácora.
  • Control: al mover un interruptor, la app manda control.php, la API guarda el nuevo estado y la Pi lo aplica en el GPIO en menos de 1 s.
  • Dos celulares: el otro celular ve el cambio en unos 3 s, con el nombre de quien lo hizo.
  • Simulación: sin sensor DHT22 los valores se simulan. Con el ventilador encendido la temperatura baja, así se nota en el gráfico durante la demo.

7. Seguridad (ISO/IEC 27400)

PrácticaCómo se aplica
Cifrado de credencialesLas contraseñas se guardan con hash bcrypt y el token de sesión con hash SHA-256. Los datos de RDS están solo en el servidor (config.php).
Datos sensibles en el celularEl token se guarda con EncryptedSharedPreferences (AES-256) y allowBackup=false.
Conexiones segurasApp ↔ Pi solo por HTTPS, y la app solo acepta el certificado de la Pi. Pi ↔ RDS con SSL.
Control de accesoRoles admin, operador y lector, revisados en cada archivo de la API.
Fuerza bruta5 intentos fallidos bloquean la cuenta por 15 minutos.
Dispositivo IoTLa Pi se identifica con una clave secreta en la cabecera X-Device-Key.
TrazabilidadTabla eventos con usuario, acción, IP y hora.
Inyección SQLTodas las consultas con datos del usuario usan mysqli_prepare.

8. Pruebas

  • Login correcto con admin y operador en dos celulares.
  • Contraseña mal 5 veces: aparece “Cuenta bloqueada”.
  • Con el rol lector los interruptores están deshabilitados.
  • Encender el ventilador en un celular: el otro lo ve en 3 s y el agente lo muestra en la consola.
  • El gráfico de 1 hora agrega lecturas nuevas cada 10 s.
  • Desactivar un usuario: su celular vuelve al login.
  • Apagar la Pi: la app muestra “Sin conexión” y no se cierra.
  • Entrar por http:// a la API: Apache lo rechaza.
